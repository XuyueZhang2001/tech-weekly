# 同类开源项目调研 · 兼论 tech-weekly 的改造方向

> 调研时间：2026-11-11
> 目的：看看别人怎么收集、怎么排序、怎么总结、怎么推送，挑出能在「纯标准库 + GitHub Actions + 每周一封邮件」约束下落地的东西。
> 所有项目数据取自 GitHub API（2026-11-11 快照），机制细节取自各仓库 README 与源码。

---

## 一、我们的基准线

先把 tech-weekly 现有能力写清楚，后面才有比较的意义。

| 维度 | 现状 | 位置 |
| --- | --- | --- |
| 信源 | 65 个，7 种类型：`rss` 49、`hackernews` 5、`arxiv` 4、`bing_news` 4、`huggingface_papers` 1、`pubmed` 1、`web_search` 1 | `config.json` |
| 配置模型 | domain → sources，字段 `type / name / url / weight`；domain 上有 `keywords`、`max_items` | `config.json` |
| 排序 | `weight × (0.45 + 0.55 × 时间衰减)`，10 天线性衰减；再叠加域名关键词命中（最多 4×1.1）、论文 +1.2、HN 热度 `points/25`（上限 9）、诉讼八卦 −14、财经 −4.5 | `main.py:904` |
| 去重 | URL 归一化 → 标题精确 → 字符 2-gram 余弦 ≥ 0.39 | `main.py:937`、`main.py:1164` |
| 配额 | 按来源数加权分配，再按来源轮转取，保证来源分散 | `main.py:1110`、`main.py:1129` |
| 摘要 | 大模型批量改写，每批 10 条，强制 JSON，落盘缓存，关闭思考模式 | `translate.py` |
| 投递 | SMTP HTML 邮件 + 纯文本副本 | `main.py` |
| 调度 | GitHub Actions，每周一 09:00 北京时间 | `weekly.yml` |

**已经做得不错、且同类项目里并不常见的**：零第三方依赖、失败降级（翻译挂了保留英文）、译文落盘缓存、来源轮转防同质化、噪声与财经词表降权。这些是后面讨论的地基，不要为了"抄"而丢掉。

## 三、六个维度横向对比

### 3.1 信源怎么组织

| 项目 | 做法 | 对我们是否有用 |
| --- | --- | --- |
| newsnow | `shared/pre-sources.ts` 单一注册表，字段 `name/color/home/column/type/interval/sub`；`interval` 枚举 2/5/10/30/60 分钟；`disable:"cf"` 可按部署环境剔除 | **有用**：`interval` 和 `column` 两个字段我们都没有 |
| DailyHotApi | 零配置，运行时扫 `src/routes/*.ts` 自动注册，新增文件即新增源 | 思路好，但我们需要静态配置 |
| miniflux | 数据库存 category + feed，OPML 导入导出，每 feed 可挂 CSS scraper / rewrite / 正则 include-exclude / 自定义 UA | **有用**：per-source 的 include/exclude 规则 |
| llm-arxiv-daily | `config.yaml` 里 `keywords: {主题: {filters: [...]}}`，拼成 `"短语"OR单词` 的 arXiv 查询串 | **有用**：arXiv 查询串可以更精确 |
| TrendRadar | 热榜走第三方 newsnow API，RSS 另有一路；`freshness_filter.max_age_days` 默认 1 天 | 参考 |

### 3.2 抓取的工程细节

| 项目 | 做法 |
| --- | --- |
| newsnow | 固定 Chrome/130 UA，`timeout:10000`，`retry:3`；TTL 30 分钟，两级缓存判定；**单源失败时回落到上次成功的 cache，返回 `status:"cache"`** |
| miniflux | `HTTP_CLIENT_TIMEOUT=20s`、`WORKER_POOL_SIZE=16`、`BATCH_SIZE=100`、`POLLING_FREQUENCY=60min`、**连续 3 次解析失败即停轮询**、`POLLING_LIMIT_PER_HOST` 同 host 限速、15MB 响应体上限；条件请求 `ETag / If-None-Match / If-Modified-Since` |
| DailyHotApi | axios `timeout=6000`，无重试，每路由自带 `Referer` + UA，node-cache + 可选 Redis |

> 我们目前只有 `urllib` 的默认超时和一层重试，**没有"失败了就用上次成功的结果"**。这一条对周报意义很大：周报是"宁缺毋滥"还是"宁滥勿缺"？偶尔某个源挂了，用上一期缓存的条目补位比整段空着好。

### 3.3 去重

| 项目 | 做法 | 备注 |
| --- | --- | --- |
| 我们 | URL 归一化 → 标题精确 → 2-gram 余弦 ≥ 0.39 | 已经比多数项目强 |
| condenseit | URL + content hash；**Jaccard 标题词集 ≥ 0.35**；语义 cosine ≥ 0.85 | Jaccard 和余弦高度重合，边际收益小 |
| ai-news-brief | **SimHash 64 位 + 汉明距离 ≤ 3** 快筛，再 pgvector 精排 | SimHash 适合万级数据，我们几十条用不上 |
| Horizon | **AI 主题去重**：输入已按分数降序，让模型只归并"同一事件"，返回 `{"duplicates":[[主索引, 重复索引…]]}`，保留组内第一个；明确反例"同一产品的不同事件不算重复，不确定就保留" | **最有价值的一条**：能处理"同事件不同标题"，cosine 抓不到 |
| TrendRadar | `guid > url` 优先级，URL 标准化清动态参数 | 我们已经做了 URL 归一化 |

### 3.4 排序与评分（差距最大的一块）

| 项目 | 机制 |
| --- | --- |
| 我们 | 规则打分：来源权重 × 时间衰减 + 关键词 + 热度 − 噪声 |
| Horizon | **每个 profile 一套 0–10 评分标准**。tech-news 五档：9–10 突破性 / 7–8 高价值 / 5–6 有趣 / 3–4 低优先 / 0–2 噪音；维度＝技术深度、新颖度、影响面、来源质量、相关性、具体证据、实质社区讨论；明确要求"不以热度等同技术重要性、不奖励夸大标题"。输出强制 JSON `{score, reason, summary, tags}`，解析失败修复一次，再失败存 `score=null`。**阈值 7.0 过滤**，配额 `max_items 20`、分组 `limit 5` |
| TrendRadar | 规则层固定加权 `rank 0.6 + frequency 0.3 + hotness 0.1`（强制和为 1.0，可配）；AI 层两阶段：先从自然语言兴趣抽 5–20 个标签，再批量给标题打 0–1 相关度，`min_score: 0.7`，`batch_size: 200` |
| ai-news-brief | LLM `importance_score` + 互动门槛（100 赞 / 50 评论）；**打分用更便宜的模型** |
| condenseit | TF-IDF + 类别 + 来源权重，**30 天半衰期衰减**，再 LLM rerank（top 30，blend 0.3） |

> 我们的关键词加分是"字符串命中"，无法判断"这条到底重不重要"。Horizon 那套 rubric 是**用一句话把编辑标准写进 prompt**，这是花小钱办大事的典型。

### 3.5 摘要与成本控制

| 项目 | 机制 |
| --- | --- |
| 我们 | 每批 10 条，强制 JSON，模型关思考模式，按内容缓存 |
| ai-news-bot | **两阶段**：Stage1 只回 JSON ID 数组（选 15–20 条），Stage2 才逐条写 4–6 句 |
| TrendRadar | `max_news_for_analysis: 150`、`include_rank_timeline: false` 省 0.5–1 倍 token、已分析条目不重复计费、翻译分批 100 条、`num_retries: 1` + `fallback_models`、提示词把格式规范移出 JSON value 减少破碎 |
| condenseit | 逐篇 JSON 含 `summary/tldr/takeaways/topics/novelty`；**日/月预算硬停**；embedding 按 URL+hash 缓存 |
| Horizon | 逐条调用（不批量）；`analysis_max_chars: 1000`（tech-news）/ 16000；`head-middle-tail` 采样；并发默认 1 + 节流；历史检索用**本地 BM25**（标题加权、中文按二字切分，无 embedding） |

> 两阶段"先选后写"是性价比最高的一条：现在 27 条每条都写摘要，但读者真正看的可能只有前 10 条。

### 3.6 投递

| 项目 | 渠道 |
| --- | --- |
| 我们 | SMTP HTML + 纯文本副本 |
| TrendRadar | 飞书/钉钉/企微/个人微信/Telegram/邮件/ntfy/Bark/Slack/webhook，按渠道字节上限分批（4000 / 20000 / 30000） |
| Horizon | Markdown 文件 / GitHub Pages / 邮件（SMTP 发 + IMAP 读订阅退订）/ webhook / 微信 iLink |
| ai-news-bot | Markdown → 内联 CSS 的 HTML 邮件 + 纯文本 alt，Gmail SMTP |
| 其余 | 无邮件 |

> 邮件这一块我们并不落后，HTML + 纯文本双版本已经是正确做法。

### 3.7 微信公众号

四个信源类项目**都没有**公众号实现：newsnow 无微信源，DailyHotApi 路由里没有 wechat，miniflux 只吃外部 RSS，llm-arxiv 与微信无关。

我们 `config.json` 里有 4 个公众号源（量子位、机器之心、新智元、PaperWeekly、阿里技术），是靠某种现成的 RSS 桥接拿到的。**这块要留意合规性**：可用的路径按优先级是①自有公众号走后台导出/接口；②获授权转载；③第三方桥接仅抓公开文章页并遵守 robots 与条款；④搜狗微信/微信读书没有公开读取 API。

## 四、值得抄的清单（按性价比排序）

### T0 · 改一次就有明显收益

| # | 机制 | 出处 | 价值 | 改动量 |
| --- | --- | --- | --- | --- |
| 1 | **LLM 相关度打分 + 阈值过滤**：一句话 rubric 写进 prompt，输出 `{score, reason}`，低于阈值直接丢 | Horizon | 高 | 小 |
| 2 | **两阶段"先选后写"**：Stage1 只让模型返回入选 ID 数组，Stage2 才写标题摘要 | ai-news-bot、TrendRadar | 高 | 小 |
| 3 | **AI 主题去重**：按分数降序喂给模型，只归并"同一事件"，输出重复组 | Horizon | 高 | 小 |
| 4 | **预算闸门**：本期 LLM 预算上限，超了就降级为"只翻译前 N 条" | condenseit | 中高 | 小 |

### T1 · 健壮性

| # | 机制 | 出处 | 价值 | 改动量 |
| --- | --- | --- | --- | --- |
| 5 | **失败回落上次成功快照**：源挂了用上期缓存条目补位 | newsnow `status:"cache"` | 高 | 中 |
| 6 | **源级超时 / UA / 重试 + 连续失败停用** | newsnow、miniflux | 中高 | 小 |
| 7 | **源健康面板**：邮件顶部列出本期异常源 | 我们的现有功能 + 增强 | 中 | 小 |
| 8 | **同 host 并发限速** | miniflux | 低（我们是顺序抓） | 中 |

### T2 · 可控性

| # | 机制 | 出处 | 价值 | 改动量 |
| --- | --- | --- | --- | --- |
| 9 | **过滤 DSL**：`field + match_type + value`，支持 all/any/none 嵌套，可表达"排除" | RSSbrew | 中 | 中 |
| 10 | **信源加 `column`/`interval` 字段**：按栏目分区、按源设抓取频率 | newsnow | 中 | 小 |
| 11 | **arXiv 查询串化**：`"短语" OR 单词`，替代现在的关键词过滤 | llm-arxiv-daily | 中 | 小 |

### T3 · 边际收益小，暂不做

- 半衰期衰减（condenseit 30 天）——我们的 10 天线性衰减够用
- SimHash + 汉明距离——数据量不到千级，2-gram 余弦足够
- ETag / If-Modified-Since 条件请求——周报每周只跑一次，命中率低
- 向量库、pgvector、embedding——违背零依赖
- 多渠道推送（Telegram/飞书/Bark）——邮件已经满足需求
- S3 远端存储、MCP 服务——对周报过重

## 五、建议的改造路线

> **进度（2026-11-11）**：阶段一已完成，落在 `curate.py` + `main.py`。
> 实测一期 60 条候选 → 24 条入选，选稿花费 ¥0.0289，中文摘要降到 ¥0.0201。
> 顺带修掉一个原有 bug：英文标题用字符 2-gram 余弦去重会误合并（见 3.3 节）。
>
> **进度（2026-11-12）**：阶段二已完成，落在 `health.py` + `main.py` + `config.json`。
> 源级 UA/超时/重试（403·404 不重试）、失败回落上期快照、连续失败冷却停抓。
> 状态存 `cache/source-state.json`（504 KB / 57 个源），靠 Actions 的 cache 跨期保留。
> T1-7「异常信源面板」确认原本就有，改为在列表里标注「已用上期快照补 N 条」。

**第一阶段（一次改动，约 150 行）**：把"选"和"写"分开
1. 抓取后先做规则粗排（保留现有打分）
2. 取前 N 条（约 40）交给模型打相关度分（T0-1），低于阈值丢弃
3. 对入选条目做 AI 主题去重（T0-3）
4. 只对最终入选的 20–24 条写标题摘要（T0-2）
5. 全程记 token 与花费，超过预算上限就截断（T0-4）

预期：**每期费用不升反降**（打分比写摘要便宜得多），但入选质量明显提升。

**第二阶段（健壮性）**：源级超时/UA/重试 + 失败回落快照 + 邮件顶部健康面板

**第三阶段（可控性）**：过滤 DSL + `column`/`interval` 字段 + arXiv 查询串

## 六、一句话结论

我们缺的不是"功能"，是**"编辑判断"**：现在靠字符串规则决定什么重要，Horizon 那套 rubric 评分 + 两阶段选稿，正好补上这一环，而且总成本还会下降。至于 TrendRadar 的多渠道推送、condenseit 的向量去重、miniflux 的 ETag 缓存，都是为它们各自的场景服务的，照搬只会把零依赖这个最大优点弄丢。
